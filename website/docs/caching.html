Multi-Level Caching

MynaDB implements a sophisticated multi-level caching architecture to maximize query performance. This guide explains the different cache layers and how to configure them.

Cache Architecture Overview

text 
┌─────────────────────────────────────────────────────────────┐
│                        Query Engine                          │
│                                                              │
│  ┌─────────────────────┐      ┌─────────────────────────┐   │
│  │   Metadata Cache    │      │   Query Result Cache    │   │
│  │  (Table info, etc.) │      │   (SQL -> Results)      │   │
│  └──────────┬──────────┘      └───────────┬─────────────┘   │
│             │                              │                  │
│             ▼                              ▼                  │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │              Parquet File Cache (Disk)                  │ │
│  │         Local SSD cache for Object Store files          │ │
│  └──────────────────────────┬──────────────────────────────┘ │
│                             │                                 │
└─────────────────────────────┼─────────────────────────────────┘
                              │
                              ▼
                 ┌─────────────────────────┐
                 │     Object Store        │
                 │  (S3, MinIO, OSS)       │
                 └─────────────────────────┘

1. Metadata Cache

The metadata cache stores table and file information to avoid expensive directory scans during query planning.

What's Cached

  • Table Info: Catalog, schema, table names, partition information
  • File Listings: List of Parquet files per partition
  • Parquet Metadata: File footers with row group statistics
  • Schema Information: Column names, types, and statistics

Cache Management API

bash 
# Get cache statistics
curl http://localhost:7000/cache/stats

# Pre-warm cache for entire catalog
curl -X POST http://localhost:7000/cache/prewarm/mydb

# Pre-warm cache for specific table
curl -X POST http://localhost:7000/cache/prewarm/mydb/default/cpu

# Clear all caches
curl -X POST http://localhost:7000/cache/clear

# Get Parquet file statistics for a table
curl http://localhost:7000/cache/parquet/mydb/default/cpu

Cache Statistics Response

2. Query Result Cache

Caches the results of SQL queries to avoid re-executing expensive queries.

Configuration

toml 
[query_cache]
# Enable query result caching
enabled = true

# Maximum cache size in MB
max_size_mb = 256

# Maximum number of cached queries
max_entries = 1000

# Cache TTL in seconds (5 minutes)
ttl_secs = 300

# Only cache queries that take longer than this (ms)
min_query_time_ms = 10

How It Works

  • Cache key is computed from: database name + SQL query text
  • Results are cached only if query execution time exceeds min_query_time_ms
  • Cache is automatically invalidated when data is written to referenced tables
  • Entries expire after ttl_secs seconds

Cache Invalidation

bash 
# Clear only query result cache
curl -X POST http://localhost:7000/cache/clear/results

# Cache is automatically invalidated on:
# - Data writes to a table
# - Compaction of a table
# - Manual flush

3. Parquet File Cache (Disk Cache)

When using Object Store backends (S3, MinIO), MynaDB can cache Parquet files on local SSD to reduce network latency.

Configuration

toml 
[file_cache]
# Enable file caching (for Object Store backends)
enabled = true

# Cache directory on local SSD
cache_dir = "/var/cache/mynadb/parquet"

# Maximum cache size (100 GB)
max_size_bytes = 107374182400

# Index save interval in seconds
auto_save_interval_secs = 300

Cache Eviction Strategy

The file cache uses a priority-based LRU eviction strategy that considers:

  • Recency: How recently was the file accessed?
  • Frequency: How often is the file accessed?
  • Partition Date: Recent partitions are prioritized (time series workloads typically query recent data)
text 
Priority Score = Recency * Frequency * Partition_Bonus

Partition Bonus:
  - Today:       10x
  - Yesterday:   8x
  - This week:   5x
  - This month:  2x
  - Older:       1x

Lower scores are evicted first.

Best Practices

For High Query Performance

  • Enable query result cache for dashboards with repeated queries
  • Pre-warm metadata cache on startup for frequently queried tables
  • Use local SSD for file cache when using Object Store
  • Set appropriate TTL based on data freshness requirements

For Memory Management

  • Monitor cache memory usage via /cache/stats
  • Adjust max_size_mb based on available RAM
  • Use min_query_time_ms to avoid caching trivial queries
  • Clear caches periodically if memory is constrained

For Object Store Workloads

  • Size file cache based on working set (recent partitions)
  • Place cache on NVMe SSD for best performance
  • Monitor cache hit rate and adjust size accordingly
  • Consider pre-warming cache for predictable query patterns

Monitoring

Monitor cache effectiveness using the stats endpoint:

bash 
# Full cache statistics
curl http://localhost:7000/cache/stats | jq .

# Key metrics to watch:
# - hit_rate: Should be > 80% for effective caching
# - memory_usage: Should not exceed configured limits
# - evictions: High eviction rate may indicate undersized cache
