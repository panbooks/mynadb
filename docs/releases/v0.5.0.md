# v0.5.0 — Distributed Database and Raft Control Plane

This milestone introduces the shared-storage distributed architecture with separate Router, Data, and Meta roles. Coordination moves from an initial etcd implementation to a built-in OpenRaft-backed Meta service within this release interval.

- **Source commit:** [`34f3bf3`](https://github.com/panbooks/mynadb/commit/34f3bf3cfd1eecf31a22c5759b22d8f5dcf0324b)
- **Changes since:** `v0.4.0` — **56 commits**, including merged branch commits where present
- **Historical development period:** January 25, 2026 – January 29, 2026

## What's included

### Cluster roles and coordination

- Add Router request handling, Data-node storage/query services, and a built-in Meta service.
- Integrate OpenRaft consensus, sled-backed state, node registration, leader forwarding, and event broadcasting.
- Add distributed query coordination, fan-out, and the initial fencing and replica-management machinery.
- Use Arrow Flight between Router and Data nodes and transfer RecordBatch data directly instead of repeatedly parsing line protocol.

### Replication and lifecycle

- Introduce warm-standby replication, cold-standby configuration, and partition-aware replica management.
- Add early object-store cluster scale-in handling and node-first storage paths.
- Add retry jitter, circuit-breaker configuration, replication CRC checks, and monitoring metrics.

### Operations and correctness

- Add role-specific TOML configuration, CLI node commands, cluster development profiles, and Kubernetes examples.
- Add Data-node HTTP monitoring, Router statistics/flush APIs, Meta HTTP inspection, and local Parquet caching.
- Fix stale table registration and query-cache invalidation after flush, plus Arrow Flight handling of view-encoded string/binary types.

## Compatibility and upgrade notes

- The initial etcd cluster module is **removed before this tag's endpoint**. Use the built-in Meta architecture and the configuration/examples in this tag.
- The executable is `mynadb`; Cargo still declares `0.2.8`. Role-specific startup is different from the earlier standalone-only service.
- Cluster storage uses node-first prefixes in this stage. Later releases revise ownership and physical partition layouts; do not assume an automatic cross-stage migration.
- The master/replica implementation from v0.2.0 remains removed and is not the basis of these cluster roles.

## Important limitations

- Router MySQL startup explicitly reports that support is not implemented; standalone MySQL connectivity does not establish availability in Router mode.
- Initial scale-in, replica, fencing, and standby designs are revised substantially in v0.6.0 and v0.7.0.
- Replication and recovery code does not establish zero downtime, lossless failover, or a production support guarantee. No multi-node fault matrix was rerun for this review.

## Building this tagged source

```bash
git clone --branch v0.5.0 --depth 1 https://github.com/panbooks/mynadb.git
cd mynadb
cargo build --locked --bin mynadb
```

The default debug executable is `target/debug/mynadb`. This tag's Cargo
package is `mynadb 0.2.8`; its package version is separate
from the retrospective release tag. Before starting a service, use configuration
from this tag and review writable data/log paths, listeners, storage credentials,
and durability settings. Build prerequisites vary across these historical snapshots.
